# Astro/Tailwind Portfolio Implementation Guide: A Waterfall Methodology

This comprehensive guide presents a waterfall-style implementation approach for building high-performance Astro/Tailwind static portfolio sites. Each phase represents a "hard gate" - do not proceed until exit criteria are fully met.

## Adapting the Methodology

While this guide presents a comprehensive waterfall approach, it can be adapted based on your specific needs:

### Waterfall-Agile Hybrid

- **Foundation First**: Use the waterfall approach for Phases 0-4 (foundation, content architecture, design system, layout/routing) to establish a stable foundation
- **Iterate Later**: Switch to a more agile approach for later phases, especially content development and UI refinement
- **Gate Critical Decisions**: Maintain strict gates around schema changes, color system updates, and other foundational elements

### Working with AI Assistants

- **Documented Context is King**: LLMs benefit from the detailed documentation, schemas, and explicit decisions generated by structured phases
- **Update Documentation First**: When requirements change, update the relevant documentation files first, then reference these in prompts
- **Context Priority**:
    1. Explicitly provided documentation/specs (most reliable)
    2. Codebase context (helpful for implementation details)
    3. Chat context (useful for immediate refinement)

### Scaling for Different Project Types

**For Simpler Portfolios**:

- Focus on Phases 0-4 + simplified versions of 7, 9, 10
- Consider creating a base template that can be easily customized
- Maintain performance and accessibility fundamentals

**For Solo Developers**:

- Phases 0 (basics), 1 (content schema), 2 (design tokens), 3 (basic linting), 4 (layout) are essential
- Simplify or defer: Complex testing (8), Storybook (5), advanced observability (10)
- Layer in complexity as needed based on project growth

## Phase 0 — Foundation Kick-off

Define the "immutable" decisions first; changing them later is painful.

|Step|Task|Notes|
|---|---|---|
|0.01|Choose package manager & scripts|Commit lock-file now to avoid npm→pnpm churn|
|0.02|Select JS runtime for tooling (ESM vs CJS)|Keeps Tailwind/ESLint configs consistent|
|0.03|Decide rendering model|Avoid React→Preact swap later; only hydrate what must be interactive|
|0.04|Scaffold mono-repo structure (if multi-site)|Ensures future shared components land in /packages|
|0.05|Initialize git hooks & CI skeleton|Pre-commit lint & type-check from day-1|
|0.06|Add Commitizen or changesets|Enables automatic semantic versioning for shared packages|
|0.07|Create Decision Record|Documents foundational choices for future reference|
|0.08|Add secret-lint pre-commit hook|Prevents accidental .env leakage|
|0.09|Prompting framework kickoff|Freeze the initial scope|
|0.10|Environment variable strategy|Prevent frantic hot-fixes to secrets later|
|0.11|Branch naming & release flow|Clear staging and deployment pipeline|

### Implementation Notes

- Document all foundational decisions in an Architecture Decision Record (ADR) for future reference
- Set up secret-lint to prevent accidental leakage of environment variables
- The mono-repo structure and changesets are optional for single-site projects but recommended if you plan to share components
- Store ADRs and other canonical documentation in `/docs/llm-context/` for easy reference in prompts

### Exit Criteria

- All immutable decisions documented in ADR
- Initial repo structure committed with lock files
- Git hooks functioning with secret-lint
- Environment variable strategy documented
- Branch strategy and release flow established
- Semantic versioning setup for shared packages (if applicable)

## Phase 1 — Content & Data Architecture

Lock the schema before writing components.

|Step|Task|
|---|---|
|1.01|Inventory all content types (case-study, blog, bio, nav)|
|1.02|Draft Astro Content-Collections schema (src/content/config.ts)|
|1.03|Generate matching TypeScript types (astro:content)|
|1.04|Create semantic URL map (slug strategy)|
|1.05|Create "Content model changelog" file to document schema evolution|
|1.06|Setup Markdown front-matter lint for duplicate-key detection|
|1.07|Add "draft" Boolean to schema to prevent accidental publishing|
|1.08|Create "validate-content-schema" test that validates required fields|
|1.09|Produce 1–2 representative MDX docs per type (fixtures)|

### Implementation Notes

- Define your [Content Collection schema](https://docs.astro.build/en/guides/content-collections/) to ensure all required fields for case studies are included and type-safe
- Include a "draft: boolean" field to safely work on content without risking accidental publication
- In your schema, include fields for process description, decision rationale, AI attribution, and outcomes
- Document every schema change in the changelog (with date and rationale) for future migrations
- Create at least one complete MDX case study to serve as a reference
- Set up linting to catch duplicate front-matter keys early
- Add a smoke test in CI that validates every MDX file has all required fields

### Exit Criteria

- Content schema fully defined with proper types
- Draft mechanism implemented
- Content model changelog file created and populated
- Markdown front-matter lint checks integrated into workflow
- Collection smoke tests added to CI
- At least one content fixture per collection is created
- URL strategy is documented and implemented

Establish consistent design foundations.

|Step|Task|
|---|---|
|2.01|Define core palette (HSL), semantic names (primary, accent, muted...) in Tailwind config|
|2.02|Typography scale → Tailwind theme.extend.fontSize|
|2.03|Spacing & radius tokens (--radius)|
|2.04|Add accessibility primitives (color-contrast tokens, focus-visible rings)|
|2.05|Include WCAG contrast target for each semantic color role|
|2.06|Create `@media (prefers-reduced-motion)` mixins/utilities|
|2.07|Store design tokens in JSON (tokens.light.json, tokens.dark.json)|
|2.08|Write "usage rules" doc (LLM prompt seed)|
|2.09|Create `scripts/build-tokens.ts` using `tailwindcss-themer` or `style-dictionary`; wire it into `pnpm build`|

### Implementation Notes

- Configure Tailwind in `tailwind.config.mjs` (note: using .mjs extension for ESM) with consistent color naming
- Establish typography scale with appropriate line heights and letter spacing
- Document WCAG contrast requirements for each semantic color role (e.g., 4.5:1 for normal text)
- Store tokens in JSON files that can generate both Tailwind config and CSS variables
- Set up a token build script that transforms JSON tokens into Tailwind config and CSS variables
- Implement accessibility primitives as part of the design system, not as an afterthought
- Create motion reduction utilities now to avoid retrofitting later
- Document usage patterns for future reference
- JSON token files can be fed directly to prompting frameworks

### Exit Criteria

- No stray hex codes in repository
- Complete Tailwind configuration with semantic naming
- JSON token files created and integrated with config
- Token build script working and integrated with build process
- Accessibility primitives implemented and documented
- WCAG contrast targets documented for each semantic color role

- Usage rules documented

## Phase 6 — Composed Sections & Islands

Implement more complex component assemblies.

|Step|Task|Notes|
|---|---|---|
|6.01|Hero, Skills grid, CaseStudyCard grid (static)||
|6.02|Decide which need interactivity → wrap in client:load islands||
|6.03|GalleryModal island with Preact||
|6.04|Accordion / ExpandableSection ↔ chevron rotation||
|6.05|Never hydrate raw `<img>` or `<a>`; use custom elements for runtime behavior||
|6.06|Implement proper ARIA for dynamic content (aria-live, focus management)||
|6.07|Snapshot tests & prefers-reduced-motion guards||
|6.08|Add motion-guard unit tests (assert prefers-reduced-motion removes transforms)||
|6.09|Client hydration audit (`pnpm astro check --diagnostics=hydration`)||
|6.10|Add "JS budget" test (dist/**/*.js !dist/**/_chunk_.js < 30 KB each)||

### Implementation Notes

- Follow Astro's Islands Architecture for selective hydration
- Use client:* directives strategically based on interaction needs:
    - client:load for immediate interaction (renders and hydrates immediately)
    - client:visible for elements that need to be interactive when in view (hydrates when visible)
    - client:idle for lower-priority interactions (hydrates after page is idle)
- Never hydrate basic elements like `<img>` or `<a>` directly; wrap in custom elements if runtime behavior is needed
- Implement proper ARIA attributes for dynamic content:
    - aria-live regions for content that updates
    - focus management for modals and accordions
    - keyboard navigation for all interactive elements
- Implement expandable sections for modular case study content
- Write tests to ensure motion reduction preferences are respected throughout the site
- Audit hydration to identify and remove unused hydrated components
- Implement JS budget test with correct glob pattern to prevent islands from growing too large

### Exit Criteria

- All composed sections render correctly
- Interactive islands function properly
- No raw elements unnecessarily hydrated
- ARIA attributes correctly implemented
- Keyboard navigation works for all interactive elements
- Interactions respect user preferences (reduced motion)
- Motion-guard tests pass for all animations/transitions
- No unused hydrated components (keeping JS size minimal)
- JavaScript bundle size for each non-chunk island stays within budget

## LLM-Assisted Development Strategy

When using the waterfall methodology with AI assistants, consider these key strategies:

### Two-Rhythm Development

|Rhythm|Purpose|Examples|
|---|---|---|
|**Waterfall Gates (P0-P4)**|Decisions that are costly to change|Package manager, schema, tokens, file structure|
|**Agile Sprints (P5-P8)**|Implementation within established guardrails|Component building, styling, content updates|

### Change Protocol

When a requirement changes that affects an earlier gate:

1. **Freeze coding** - Pause implementation work
2. **Update canonical documentation** - Change the schema, token file, or design guideline
3. **Commit changes** - Push documentation updates first
4. **Re-ingest into LLM** - Update the LLM's context with the new documentation
5. **Resume development** - Continue with updated context

### Effective LLM Prompting

- Use the JSON token files directly in prompts for consistent styling
- Reference the content schema when requesting content-related components
- Create prompt templates for common tasks (component creation, testing, refactoring)
- Use diff-style prompts for iterative refinements

### Context Management

Prioritize context sources in this order:

1. **Canonical documentation** - Schema, design tokens, architecture diagrams
2. **Code structure** - Repository organization, component patterns
3. **Immediate task context** - Current problem and constraints

This structure allows for stable foundations with rapid, flexible implementation, making the most of AI assistance while maintaining architectural integrity.

## Balancing Structure and Flexibility

### Benefits of the Waterfall Approach

- **Prevents costly rework**: Establishing foundations like content schema and design tokens early prevents expensive changes later
- **Enforces quality gates**: Each phase has clear exit criteria, maintaining high standards
- **Ensures performance**: Building performance in from the start is easier than retrofitting it
- **Improves accessibility**: A11y becomes integrated rather than an afterthought
- **Creates documentation naturally**: Each phase produces documentation that serves as future reference

### Addressing Common Concerns

#### Rigidity and Overhead

- **Concern**: The structured approach can feel rigid and may slow initial visible progress
- **Mitigation**:
    - Complete foundation phases quickly (0-4) to reach visible implementation sooner
    - Use the foundation as guardrails, not limitations
    - Document decisions concisely without excessive formality

#### Change Management

- **Best Practice**: When requirements change, update documentation first
- **Process**:
    1. Update the affected documentation (schema, design tokens, etc.)
    2. Note the change in the content model changelog
    3. Implement the change with clear references to updated documentation
    4. Test against the expanded requirements

#### Time Constraints

- **For tight deadlines**: Focus on Phases 0-4, then a minimal version of Phases 7, 9, and 10
- **Prioritize**: Core content architecture, basic design system, and deployment essentials
- **Defer**: Complex testing, Storybook, advanced observability until after initial launch

### Measuring Success

Rather than perfect adherence to every step, success should be measured by:

1. **Performance**: Lighthouse scores meeting targets
2. **Maintainability**: Clean, consistent codebase with clear patterns
3. **Accessibility**: Meeting WCAG standards
4. **Content flexibility**: Schema supporting both current and anticipated needs
5. **Developer experience**: Smooth workflow without excessive friction
